# 工作流操作系统（WORKFLOW.md）

> 这是项目无关的母版操作手册。新项目用 BOOTSTRAP.md 生成实例；本文件解释这套为什么这样设计。

## 内核（迁移时真正要复制的三条，别只搬模板）
1. **范围外化成 binding 清单**（OUT-OF-SCOPE）——防漂移的命根子，也是"会规划不收尾"的解药。
2. **小单元，闭环了才进下一个**（Done-when + allowlist + verify + STOP）——把"计划"变"出货"的引擎。
3. **判断与执行分离，人按异常介入**——你从"逐步把关"升级到"只在闸门处停"。
> 丢了这三条的魂、只搬了表格，就会退回 vibe coding。

## 三角色三闸门
- 规划者（便宜）：定"做什么 + 怎么拆 + 验收标准"，写 prompt。
- 执行者（贵）：只执行，不替你做产品决策。
- 裁判（verifier，自动）：验正确性。
- 人（你）：品味/方向闸门，按"异常"介入，不逐步把关。
> 单 Agent 场景：规划+执行塌成一个，必须靠 /goal 这道墙把两者重新分开。

## 七条原则
1. 小而可独立验收的单元；每个带 Done-when + 文件 allowlist。
2. 范围写下来并 binding；维护 OUT-OF-SCOPE + V2-BACKLOG；越界先出声。
3. 把正确性闸门自动化，人这道闸门才改成"按异常停"。
4. 思考前置；记忆文件 = 共享记忆，每次开工有据。
5. 锁定目标(/goal) 与执行目标(/loop) 分离。
6. 循环对症：收敛型(达标即停) vs 爬升型(指标驱动)。
7. 爬升型必须先造尺→校尺→再爬；尺子本身会歪，先校准。

## 选哪种循环
- 完成标准能写成"通过/不通过"？→ 收敛型。
- 目标是"更好/更地道/更准"程度问题？→ 先建 eval（测试集+rubric+打分）、校准打分器，再爬升；平台期停。

## 档位（默认 Lite，Full 要"挣"）
- **Lite**：小工具/脚本 → CLAUDE.md + 清单式 PLAN，跳过 PRD。
- **Full**：多周项目 → core + project rules + PRD + PLAN + CLAUDE.md + verifier。
- **Eval-driven**：目标是质量/指标 → Full + eval harness。

## 完成信号怎么定（verifier 的根）
- 有 build/test → 直接用。
- 有指标/eval → 用分数（先校尺）。
- 只能人工 → "完成"写成可勾选验收清单，你当裁判；verifier 退化为"清单核对 + 查 allowlist 越界"。
- 分层混合：纯逻辑层自动验，集成/UI 层清单+冒烟。

## 随成熟度降档
项目进入维护期：PLAN 塌缩成 progress log；PRD 冻结只读；只留 CLAUDE.md + verifier。脚手架随成熟缩水，别背死仪式。
